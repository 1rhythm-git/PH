PH / Infinite Climb
Codex Master Project Brief
________________________________________
0. 문서 목적
이 문서는 Unity 프로젝트 PH의 전체 개발 기준을 정의한다.
현재 프로젝트는 기존 Unity 콘텐츠를 모두 삭제하고, Codex 설정만 유지한 상태에서 새로 시작한다.
이전 프로젝트의 코드, 테스트 오브젝트, 임시 로직, 사용하지 않는 시스템은 복구하지 않는다.
Codex는 이 문서를 프로젝트의 최상위 기획 기준으로 사용한다.
기능을 구현할 때 이 문서와 충돌하는 구조를 임의로 만들지 않는다.
________________________________________
1. 개발 환경
1.1 Unity 버전
Unity 6.3 LTS 기준으로 개발한다.
기준 버전:
6000.3.0f1
1.2 입력 시스템
Unity Input System의 New 방식만 사용한다.
사용하지 않는 방식:
•	Legacy Input Manager
•	Active Input Handling Both
•	UnityEngine.Input 기반 입력
1.3 대상 플랫폼
우선 대상 플랫폼은 Android이다.
추후 다음 플랫폼을 고려한다.
•	iOS
•	WebGL
1.4 화면 방향
세로형 모바일 게임이다.
기준 화면비는 9:20이다.
가로 방향에는 항상 8개의 셀이 모두 보여야 한다.
세로 방향은 기본적으로 10개 층을 표시한다.
________________________________________
2. 프로젝트 핵심 콘셉트
플레이어가 건물 내부를 계속 위로 올라가는 무한 상승형 하이퍼 캐주얼 게임이다.
플레이어는 각 층에서 좌우로만 움직일 수 있다.
각 층을 이동하며 적과 장애물을 피하고, 셀 내부에 배치된 아이템을 획득한다.
플레이어는 엘리베이터 또는 층 이동 지점에 도달해 다음 층으로 올라간다.
게임은 플레이어가 사망하거나 제한 시간이 종료될 때까지 계속된다.
특정 층을 완료하거나 스테이지를 클리어하는 구조가 아니다.
________________________________________
3. 핵심 게임 루프
게임의 기본 흐름은 다음과 같다.
1.	플레이어가 1층 왼쪽 지점에서 시작한다.
2.	현재 층에서 좌우로 이동한다.
3.	적과 장애물을 피한다.
4.	셀 내부의 아이템을 통과해 획득 조건을 충족한다.
5.	엘리베이터 또는 다음 층 이동 지점까지 도달한다.
6.	다음 층으로 이동한다.
7.	층이 올라갈수록 진행 기록과 점수가 누적된다.
8.	하트가 0이 되거나 시간이 0이 되면 게임이 종료된다.
9.	사망 시점까지 도달한 최고 층과 점수를 기록한다.
________________________________________
4. 무한 상승 구조
4.1 절대 층수
플레이어의 진행은 실제 층수로 관리한다.
예시:
•	1F
•	2F
•	10F
•	11F
•	37F
•	125F
게임 결과와 랭킹에는 절대 층수만 사용한다.
4.2 내부 페이지
성능과 화면 구성을 위해 내부적으로 10층 단위 페이지를 사용한다.
예시:
•	Page 0: 1F ~ 10F
•	Page 1: 11F ~ 20F
•	Page 2: 21F ~ 30F
페이지는 개발용 내부 단위이다.
플레이어에게 다음 표현을 표시하지 않는다.
•	Stage 1
•	Stage 2
•	Page 1
•	Page Clear
•	Next Stage
•	Clear
4.3 게임 종료
다음 조건이 발생할 때만 한 번의 플레이가 종료된다.
•	하트가 0이 됨
•	제한 시간이 0이 됨
플레이어가 10층, 20층, 100층에 도달해도 게임은 종료되지 않는다.

5. 게임 화면 구조
5.1 기본 그리드
한 페이지는 다음 크기로 구성한다.
•	가로: 8셀
•	세로: 10층
•	총 셀: 80개
좌표 원점은 왼쪽 아래이다.
Cell_0_0 = 왼쪽 아래
셀 생성 순서:
1.	왼쪽에서 오른쪽
2.	한 줄 완료 후 위층
3.	다시 왼쪽에서 오른쪽
5.2 수평선
층 경계에는 수평선을 표시한다.
10층 기준 총 11개의 수평선이 존재한다.
Line_H_0
Line_H_1
...
Line_H_10
5.3 수직 경계
가로 8셀 기준 수직 경계는 9개이다.
Line_V_0
Line_V_1
...
Line_V_8
수직 경계는 기본 그리드 표시용으로 항상 보이지 않는다.
적의 이동 경로나 EnemyTrail 표현에 사용한다.
________________________________________
6. 플레이어 시스템
6.1 이동
플레이어는 현재 층에서 좌우로만 이동한다.
수직 이동은 직접 입력으로 수행하지 않는다.
다음 층 이동은 엘리베이터 또는 층 이동 시스템이 담당한다.
6.2 생성
플레이어는 InGame 씬에 미리 배치하지 않는다.
Lobby에서 선택된 플레이어 프리팹을 InGame 진입 시 런타임 생성한다.
6.3 캐릭터
최소 2개 이상의 플레이어 캐릭터를 지원할 수 있어야 한다.
캐릭터 데이터는 추후 ScriptableObject 기반으로 분리할 수 있도록 설계한다.
현재 기본 캐릭터 슬롯은 스파이 콘셉트 캐릭터이며, 두 번째 캐릭터 슬롯은 닌자 콘셉트 캐릭터이다.
두 캐릭터 모두 다음 애니메이션 리소스 구조를 사용한다.
•	Idle 2프레임 반복
•	Walk 2프레임 반복
•	Run 2프레임 반복
•	캐릭터 선택 화면용 정면 이미지 1장
기본 이동 애니메이션은 Idle과 Walk를 사용한다.
Run 애니메이션은 이동속도 아이템 효과가 활성화된 동안 대시 애니메이션으로 사용한다.
6.4 이동 방향 전환
플레이어는 아이템 획득 조건을 충족하기 위해 같은 층을 여러 차례 좌우로 왕복할 수 있다.
따라서 층 이동은 강제 자동 진행만으로 만들지 않는다.
플레이어가 현재 층에서 아이템 획득을 위해 충분히 왕복할 수 있어야 한다.
6.5 이동 제한
플레이어는 좌측 끝 셀과 우측 끝 셀의 중심을 넘지 않는다.
좌우 끝에 도달하면 벽에 부딪혀 밀리는 방식이 아니라 해당 방향을 바라본 뒤 Idle 상태로 정지한다.
엘리베이터 위치에 도달했을 때도 먼저 피벗 후 Idle 상태로 전환하고, 이후 엘리베이터 상승을 시작한다.
________________________________________
7. 하트와 사망
7.1 하트
초기 하트는 3개이다.
HP 게이지는 사용하지 않는다.
7.2 피격
적 또는 위험 요소와 충돌하면 하트가 1개 감소한다.
7.3 리스폰
하트가 남아 있으면 안전한 위치로 리스폰한다.
물리 충돌로 플레이어를 밀어내는 방식은 사용하지 않는다.
끼임 방지를 위해 즉시 안전 지점으로 이동시킨다.
7.4 게임 모드
Lobby에서 게임 모드를 선택할 수 있다.
Normal
현재 층 또는 현재 진행 위치 기준 안전 지점으로 리스폰한다.
Hard
피격 후 항상 1층부터 다시 시작한다.
단, 한 번의 플레이 기록이 초기화되는지는 별도 밸런스 정책으로 관리한다.
기본 권장안은 Hard에서도 해당 플레이의 최고 도달 층 기록은 유지하는 것이다.
________________________________________
8. 시간 제한
게임에는 제한 시간이 존재한다.
시간이 0이 되면 Time Over 처리 후 Game Over가 된다.
시간 값은 Inspector 또는 ScriptableObject에서 조정 가능해야 한다.
추후 아이템 효과로 시간을 증가시키거나 감소시킬 수 있어야 한다.
________________________________________
9. 층 밝기와 가시성
각 층은 다음 상태 중 하나를 가진다.
Current Floor
플레이어가 현재 위치한 층이다.
완전히 밝게 표시한다.
Past Floor
이미 지나간 층이다.
약간 어둡게 표시한다.
Future Floor
아직 도달하지 않은 층이다.
검게 가린다.
기존 FogTile 방식은 사용하지 않는다.
UI 또는 전용 가시성 레이어를 사용한다.

10. 적 시스템
10.1 기본 적 수
한 페이지당 기본 적 수는 7개이다.
값은 Inspector 또는 설정 데이터에서 변경할 수 있어야 한다.
10.2 이동
적은 특정 수직 경계선을 따라 위아래로 이동한다.
10.3 시작 위치
적은 현재 페이지의 상단 수평선 기준으로 생성된다.
10.4 렌더링
적은 다음 요소보다 앞에 보여야 한다.
•	배경
•	그리드
•	라인
•	가시성 레이어
현재 테스트 Enemy는 경찰 이미지 1장 PNG를 사용한다.
별도 프레임 애니메이션 없이 단일 스프라이트를 Enemy Visual에 표시한다.
히트박스는 테스트 단계에서만 표시하며, 일반 플레이 중에는 숨긴다.
10.5 새 페이지
플레이어가 새로운 10층 구간에 진입하면 해당 페이지의 적을 생성한다.
지나간 페이지의 적은 제거하거나 풀로 반환한다.
10.6 Game Over 정지
Game Over 또는 Time Over 결과창이 표시되면 Enemy 이동, 충돌 판정, 바닥/천장 충돌 사운드는 즉시 정지한다.
Enemy Spawner도 함께 비활성화하여 결과창 이후 새 Enemy가 생성되지 않도록 한다.

11. EnemyTrail 시스템
적이 아래로 이동할 때 수직 이동 흔적이 생성된다.
적이 위로 이동할 때 해당 흔적이 삭제된다.
수직 라인은 처음부터 전부 표시하지 않는다.
수직 라인은 다음 기준을 지킨다.
•	페이지 상단 수평선에서 시작
•	페이지 하단 수평선을 넘지 않음
•	수평선과 빈틈 없이 연결
•	T자 또는 역T자 접합이 자연스럽게 보임
•	적의 움직임과 라인 길이가 동기화됨
라인 스프라이트는 Unity Square Sprite를 사용할 수 있다.
권장 기준:
•	Sprite: Square
•	PPU: 256
•	Draw Mode: Simple

12. 아이템 시스템
아이템은 각 셀 내부에 배치된다.
플레이어가 아이템의 획득 판정 영역을 통과하면 통과 횟수가 증가한다.
일부 아이템은 한 번 통과하면 획득한다.
일부 아이템은 같은 아이템을 여러 차례 통과해야 획득한다.
12.1 기본 획득 방식
아이템마다 필요한 통과 횟수를 가진다.
예시:
•	필요 통과 횟수 1: 한 번 통과하면 획득
•	필요 통과 횟수 3: 세 번 통과하면 획득
•	필요 통과 횟수 5: 다섯 번 통과하면 획득
플레이어는 같은 층에서 좌우로 여러 번 왕복하면서 아이템을 통과할 수 있다.
필요 횟수가 충족되면 아이템이 획득된다.
12.2 통과 판정 기준
통과 횟수는 단순 충돌 프레임 수로 계산하지 않는다.
한 번 진입하고 완전히 빠져나온 뒤 다시 진입했을 때 다음 통과로 인정한다.
플레이어가 아이템 콜라이더 내부에 머무르는 동안 횟수가 반복 증가하면 안 된다.
권장 판정 흐름:
1.	플레이어가 아이템 판정 영역 진입
2.	아직 현재 진입을 기록하지 않았다면 통과 횟수 1 증가
3.	플레이어가 아이템 판정 영역 이탈
4.	다음 진입 가능 상태로 전환
5.	다시 진입하면 새로운 통과로 인정
12.3 통과 방향
기본적으로 좌→우와 우→좌 통과를 모두 유효한 통과로 인정한다.
추후 일부 아이템은 특정 방향 통과만 인정할 수 있도록 확장 가능하게 설계한다.
12.4 통과 진행 표시
여러 번 통과해야 하는 아이템은 현재 진행 상태를 시각적으로 보여줄 수 있어야 한다.
예시:
•	1 / 3
•	2 / 3
•	원형 게이지
•	색상 변화
•	스프라이트 단계 변화
초기 구현에서는 텍스트 또는 간단한 게이지를 사용할 수 있다.
현재 구현에서는 남은 통과 횟수를 아이템 중앙 숫자로 표시한다.
숫자는 흰색 Bold 텍스트를 사용하고, 검은 Outline과 Shadow를 적용해 배경과 아이콘 위에서도 시인성을 확보한다.

13. 아이템 분류
아이템은 크게 세 종류로 나눈다.
13.1 스코어형 아이템
획득 즉시 현재 플레이 점수에 반영된다.
예시 효과:
•	고정 점수 추가
•	현재 점수 배수 증가
•	연속 획득 콤보 증가
•	특정 시간 동안 점수 획득량 증가
스코어형 아이템은 영구 데이터가 아니라 현재 런의 점수에 영향을 준다.
13.2 스킬형 아이템
획득 즉시 또는 일정 시간 동안 스킬 효과가 발동한다.
초기 출시 범위에서는 플레이어에게 영향을 주는 효과를 중심으로 구성한다.
현재 효과:
•	이동 속도 증가
•	하트 회복
•	시간 증가
•	Max Life 증가
추후 레벨 디자인 검토 효과:
•	무적
•	아이템 자동 획득 범위 증가
•	적 충돌 무시
•	점수 배수 증가
•	적 이동 속도 감소
Enemy 일시 정지는 플레이 흐름을 끊는 효과로 판단해 기획 범위에서 제외한다.
스킬 효과는 지속 시간, 중첩 여부, 재획득 처리 방식을 데이터로 설정할 수 있어야 한다.
현재 구현된 스킬형 아이템:
•	Red Sneaker: 이동속도 소폭 상승
•	Winged Shoe: 이동속도 대폭 상승
•	Winged Heart: 런 중 1회 Max Life +1
이동속도 상승은 영구 적용하지 않는다.
기본 `EffectDurationSeconds` 5초에 1~3 랜덤 카운트를 곱한 시간 동안 적용하고, 지속시간이 끝나면 기본 이동속도로 복구한다.
지속시간 동안 플레이어 캐릭터는 점멸, Run 애니메이션, 강화된 대시 먼지 연출을 표시한다.
현재 구현을 스킬형 아이템의 기반 완료 상태로 보고, 추가 효과와 수치는 추후 레벨 디자인 단계에서 보완한다.
13.3 수집형 아이템
획득 후 현재 플레이를 넘어 장기 진행에 영향을 준다.
예시:
•	업적 진행도
•	도감 등록
•	컬렉션 완성
•	패시브 능력 강화
•	기본 이동 속도 증가
•	시작 하트 증가
•	시작 시간 증가
•	캐릭터 스탯 강화
•	신규 캐릭터 또는 외형 해금
수집형 아이템은 로컬 저장 및 추후 뒤끝 서버 저장 대상이다.

15. 아이템 배치
아이템은 각 셀 내부에 배치할 수 있다.
아이템은 셀의 중앙 또는 설정된 로컬 오프셋 위치에 생성한다.
한 셀에 배치 가능한 아이템 수는 기본적으로 1개이다.
추후 복수 배치를 지원할 수 있도록 셀과 아이템의 결합을 강하게 만들지 않는다.
아이템 배치는 다음 방식 중 하나를 지원할 수 있다.
•	고정 배치
•	랜덤 배치
•	층 구간별 테이블
•	난이도 기반 배치
•	ScriptableObject 패턴 기반 배치
초기 단계에서는 랜덤 배치와 고정 테스트 배치를 지원하는 구조를 권장한다.
현재 구현에서는 실행 시점마다 런타임 시드를 새로 생성해 페이지별 아이템 배치에 반영한다.
따라서 게임을 새로 실행하면 같은 페이지라도 아이템 위치와 종류가 달라질 수 있다.
디버그나 재현 테스트가 필요할 때는 `randomizeSeedOnStart`를 끄고 고정 `randomSeed`를 사용한다.

15.1 캐릭터 스테이터스
캐릭터는 종류마다 외형과 기본 스테이터스가 다르게 적용된다.
캐릭터는 지속적인 업데이트로 추가될 수 있으므로 코드에 고정하지 않고 데이터 에셋 또는 서버 데이터로 확장 가능한 구조를 유지한다.

기본 캐릭터 스테이터스:
•	이동속도
•	방향전환 쿨타임
•	부스터 게이지
•	MaxLife
•	아이템 즉시 획득 확률
•	캐릭터 레벨과 경험치(XP)
•	스킬형 아이템 Page 출현 확률(Chance)

캐릭터별 레벨업 필요 경험치는 `CharacterDefinition`의 레벨별 테이블에서 관리한다.
획득 경험치의 최종 결과식과 런 결과 연동은 추후 점수/결과 시스템 정리 시 확정한다.
현재 진행 상태 API는 경험치 누적과 연속 레벨업을 지원하며, 저장 연동 전까지 세션 단위로 유지한다.

캐릭터 고유 스킬은 지정 레벨에 도달하면 자동 활성화한다.
InGame HUD에는 고유 스킬을 별도 표시하지 않고 실제 버프만 적용한다.
Lobby 캐릭터 설명에는 해금 전 잠금 레벨과 설명을 표시하고, 해금 후 활성 상태와 Chance 수치를 표시한다.
현재 스킬형 아이템 Page Chance는 페이지 생성 시 Time 또는 Skill 타입 아이템 1개를 보장할 추가 확률이며, 기존 아이템 가중치 추첨은 그대로 유지한다.

부스터 게이지는 이동거리와 방향전환에 따라 축적된다.
현재 피버 게이지 증가량은 모든 캐릭터에서 기존 캐릭터별 설정값의 30%로 조정한다.
게이지가 100%에 도달하면 캐릭터 고유 스킬 버튼이 아니라 피버타임 발동 자원으로 사용한다.
피버타임은 별도 수동 조작을 추가하지 않고, 100% 도달 후 다음 방향전환 시 자동 발동하는 방향을 기본 정책으로 둔다.
피버타임 중에는 짧은 시간 동안 이동, 아이템, Enemy 회피 또는 점수 관련 보너스를 제공할 수 있다.
캐릭터별 차이는 별도 스킬 버튼이 아니라 피버타임 효과 차별화로 확장한다.

아이템 즉시 획득 확률은 아이템의 RequiredPassCount를 무시하고 한 번에 획득할 확률이다.
이 확률은 서버 검증형 아이템 또는 랭킹 검증 정책과 충돌할 수 있으므로, 저장/랭킹 데이터에는 캐릭터 ID와 캐릭터 스탯 버전이 포함되어야 한다.

캐릭터 획득 경로:
•	게임머니 구매
•	광고보상
•	업적 보상
•	이벤트 지급
•	추후 패키지/상점 판매

구현 방향:
•	캐릭터별 값은 `CharacterDefinition` 같은 데이터 에셋으로 관리한다.
•	런타임에는 선택된 캐릭터 데이터를 Player, HUD, Item 시스템에 주입한다.
•	Lobby 캐릭터 선택/보유 상태와 InGame 적용 상태는 분리한다.
•	캐릭터 구매/보유/장착 상태는 저장 시스템 또는 BackND 연동 시 별도 모델로 관리한다.

현재 캐릭터 구성:
•	AgentX: 스파이 콘셉트, 기본 로비 선택 캐릭터, Lv.3 Gadget Forecast(Time/Skill Chance 15%) 해금
•	Alice: 금발 양갈래 메이드와 빨간 토끼귀 머리띠 콘셉트, AgentX 기동/피버/Chance 스테이터스 1.5배, MaxLife 3
•	Landy: 힙합 모자, 선글라스, 금목걸이를 착용한 고릴라 콘셉트, AgentX 기동/피버/Chance 스테이터스 1.2배, MaxLife 4
•	Ninja: 닌자 콘셉트, 기존 세모 캐릭터 슬롯을 대체, Lv.4 Swift Supply(Time/Skill Chance 20%) 해금
현재 스테이터스는 캐릭터 간 밸런스 테스트를 위해 데이터 에셋에서 조정한다.
현재 생명력은 AgentX 3, Alice 3, Landy 4, Ninja 2로 설정한다.
로비 표시 순서는 AgentX, Landy, Alice, Ninja 순서이며 InGame 단독 실행 fallback은 AgentX를 사용한다.

16. 점수 시스템
점수는 최고 도달 층과 별도로 관리한다.
16.1 최고 도달 층
플레이어가 해당 런에서 도달한 가장 높은 절대 층수이다.
무한 상승 구조이더라도 Game Over 시점에는 해당 런의 최고 도달 층을 반드시 확정한다.
이 값은 Game Over 결과 화면, 저장 데이터, 랭킹 제출, Floor Score, Line Bonus 계산의 기준값이다.
16.2 플레이 점수
현재 런에서 획득한 점수이다.
점수는 다음 요소의 영향을 받을 수 있다.
•	층 상승
•	스코어형 아이템
•	콤보
•	난이도 배율
•	스킬 효과
16.3 런 종료 점수 계산
현재 게임은 무한 상승 구조이므로 런 종료는 Game Over로 통일한다.
Game Over가 발생하면 먼저 runHighestFloor를 확정하고, 확정된 runHighestFloor를 기준으로 점수를 계산한다.

Game Over 시 총점은 다음 값으로 계산한다.
•	Floor Score: floorMoveCount × floorScoreValue
•	Line Bonus: floor(lineEfficiencyRatio, 1) × lineScoreBonusValue

Game Over 총점:
Total Score = Floor Score + Line Bonus

floorMoveCount는 Game Over 시 확정된 runHighestFloor 기준으로, 시작 층 이후 실제로 상승한 층 수이다.
예시:
•	1F에서 Game Over: 0
•	2F에서 Game Over: 1
•	10F에서 Game Over: 9

Time Bonus와 Life Bonus는 기본 점수 공식에서 제외한다.
남은 시간과 남은 생명력은 결과 화면의 참고 정보로 표시할 수 있지만, 기본 총점에는 반영하지 않는다.

16.3.1 Game Over 결과창과 광고 부활
Game Over 결과창에는 기본적으로 결과 확인 후 Lobby로 복귀하는 버튼을 제공한다.
추후 Google AdMob 보상형 광고를 붙일 때는 결과창에 광고보기 버튼을 추가할 수 있다.
플레이어가 광고보기를 선택하고 보상형 광고 시청을 정상 완료하면 해당 런을 즉시 종료하지 않고 부활 처리한다.

광고 부활 기본 규칙:
•	한 런에서 광고 부활 가능 횟수는 기본 1회로 제한한다.
•	광고 시청 완료 보상이 확인된 경우에만 부활한다.
•	광고 로드 실패, 시청 취소, 보상 미지급 상태에서는 부활하지 않고 결과창을 유지한다.
•	부활 시 HP, 타이머, 플레이어 위치, 무적 시간, 적/아이템 상태 복구 규칙을 명확히 정의해야 한다.
•	Time Over와 Life Depleted 중 어떤 종료 사유에서 광고 부활을 허용할지 별도 정책으로 관리한다.
•	광고 부활이 발생한 런은 결과 데이터에 reviveUsed, reviveSource, reviveCount 같은 필드를 남겨 저장/랭킹 검증에 활용한다.
•	BackND 저장 및 랭킹 업로드 시 광고 부활 사용 여부를 함께 전송할 수 있어야 한다.

구현 시 Google AdMob SDK 직접 호출은 GameStateController나 결과창 UI에 직접 넣지 않는다.
보상형 광고는 IRewardedAdService 같은 인터페이스 뒤에 두고, 결과창은 광고 요청/성공/실패 이벤트만 사용한다.

16.4 돌파 보너스 검토
돌파 보너스는 과거 프로젝트에서 플레이어가 세로 라인을 적게 통과할수록 높은 점수를 받도록 설계된 보너스이다.
현재 프로젝트의 수직 경계 Line_V_0 ~ Line_V_8은 적 이동 경로와 EnemyTrail 표현에도 사용되므로, 점수 계산용 통과 카운터는 렌더링 라인과 분리해야 한다.

현재 구조에서도 Game Over 시 도달 층수를 기반으로 돌파 보너스를 산정할 수 있다.
기준은 "Game Over 시 확정된 runHighestFloor까지 진행하는 데 필요한 최소 세로 경계 통과 수"와 "실제 세로 경계 누적 통과 수"의 비율이다.

권장 계산 흐름:
1.	Game Over 시 runHighestFloor를 확정한다.
2.	runHighestFloor로 floorMoveCount를 계산한다.
3.	각 층의 시작 컬럼과 목표 컬럼을 기준으로 최소 세로 경계 통과 수를 계산한다.
4.	최소 세로 경계 통과 수는 시작 층이 아니라, 실제 상승해 통과한 층 구간만 포함한다.
5.	고정 좌측 시작 → 우측 도착 구조라면 기본 최소값은 floorMoveCount × minVLinePassPerFloor로 계산한다.
6.	8컬럼 기준 내부 세로 경계만 점수 대상으로 삼으면 minVLinePassPerFloor 기본값은 7이다.
7.	실제 통과 수 passedVLineCount는 런 중 플레이어가 통과한 세로 경계 누적 횟수로 기록한다.
8.	lineEfficiencyRatio = minimumRequiredVLinePassCount / max(passedVLineCount, minimumRequiredVLinePassCount)
9.	lineEfficiencyRatio를 소수 첫째 자리에서 내림 처리한다.
10.	Line Bonus = floor(lineEfficiencyRatio, 1) × lineScoreBonusValue

이 방식에서는 실제 통과 수가 최소 통과 수와 같을 때 최대 효율 1.0을 받는다.
왕복, 아이템 재통과, 불필요한 이동으로 passedVLineCount가 증가하면 효율이 낮아진다.
따라서 Game Over 시점까지 더 높은 층에 도달하면서도 세로 라인 통과를 최소화하는 플레이가 고점 목표가 된다.

구현 시 필요한 조건:
•	플레이어의 좌우 이동 중 셀 경계 통과를 감지하는 PlayerLinePassTracker가 필요하다.
•	같은 경계선 위에서 머무르거나 떨림이 발생해도 중복 카운트되지 않아야 한다.
•	층 이동, 리스폰, 페이지 전환 시 중복 계산 방지 상태를 초기화해야 한다.
•	리스폰으로 위치가 바뀔 때는 순간이동 경로를 통과 수로 계산하지 않는다.
•	엘리베이터 또는 층 이동 연출 중 자동 위치 보정은 통과 수로 계산하지 않는다.
•	minimumRequiredVLinePassCount가 0인 경우 Line Bonus는 0으로 처리한다.
•	층별 시작/목표 컬럼이 달라질 수 있으므로 minVLinePassPerFloor는 고정값이 아니라 층 데이터에서 계산할 수 있게 열어둔다.

16.5 기록 분리
다음 값은 분리해서 저장한다.
•	Current Floor
•	Run Highest Floor
•	Best Highest Floor
•	Current Run Score
•	Best Score
랭킹 기준은 별도로 선택 가능하게 설계한다.
초기 권장 기준:
•	메인 랭킹: 최고 도달 층
•	보조 랭킹: 최고 점수

캐릭터 초상화 기본 규격:
•	캔버스는 1024×1536 RGBA PNG와 투명 배경을 사용한다.
•	캐릭터는 2등신 전신 픽셀아트로 제작하고 원본 비율을 유지한다.
•	캐릭터 높이는 캔버스의 약 60~72% 범위로 제한하고 수직 중앙보다 약간 위에 배치한다.
•	Point 필터, Mipmap Off, Alpha Is Transparency 설정을 사용한다.
캐릭터 애니메이션 기본 규격:
•	Idle 2, Walk 2, Run 2의 6프레임으로 구성한다.
•	6프레임은 정면이 아닌 화면 오른쪽을 향한 측면 기반으로 제작한다.
•	얼굴, 몸통, 골반, 발이 동일한 측면 방향을 유지해야 한다.
•	Walk와 Run 2프레임은 좌우 손발이 확실히 교차되는 반대 포즈로 제작한다.
•	두 프레임에서 같은 손과 같은 발이 계속 앞에 남아 있으면 걷거나 달리는 느낌보다 캐릭터가 끌려가는 느낌이 강해지므로 금지한다.
•	Walk는 앞발 접지와 뒷발 회수, Run은 더 큰 보폭과 팔 스윙 및 공중감을 명확히 구분한다.
•	화면 왼쪽 이동은 런타임 Sprite 좌우 반전으로 처리한다.
•	개별 프레임은 398×435 RGBA PNG를 사용한다.
추후 추가 가능:
•	수집 아이템
•	캐릭터 강화
•	업적
•	로그인
•	랭킹

19. 서버 연동 준비
현재 단계에서 뒤끝 SDK를 반드시 설치할 필요는 없다.
그러나 서버를 나중에 연결할 때 게임 코드를 크게 수정하지 않도록 인터페이스 기반으로 설계한다.
게임 플레이 코드는 뒤끝 SDK를 직접 호출하지 않는다.

인터넷 연결이 없어도 게임 플레이가 가능해야 한다.

다음 로그인 또는 네트워크 복구 시 서버로 재전송할 수 있어야 한다.
최고 층, 최고 점수, 수집형 아이템 데이터는 동기화 충돌 가능성을 고려해야 한다.
초기 정책은 더 높은 기록과 더 많은 수집 진행도를 우선하는 방식으로 설계할 수 있다.

25. SOLID 적용 기준
기능 안정성과 최소 변경을 최우선으로 한다.
단일 책임
예시:
•	PlayerMotor: 이동만 담당
•	PlayerHealth: 하트만 담당
•	ItemPassDetector: 통과 판정만 담당
•	ItemEffectManager: 아이템 효과 실행
•	ScoreManager: 점수 계산
개방 폐쇄
새로운 아이템이 추가될 때 기존 ItemManager의 거대한 switch 문을 수정하는 구조를 피한다.
아이템 효과는 인터페이스 또는 효과 클래스를 통해 확장한다.
인터페이스 분리
인증, 저장, 랭킹, 업적, 인벤토리를 하나의 거대한 서버 인터페이스로 합치지 않는다.
의존성 역전
게임 플레이 클래스가 뒤끝 SDK나 구체 저장 클래스에 직접 의존하지 않는다.

27. 최상위 개발 원칙
1.	게임은 무한 상승 구조이다.
2.	플레이어는 사망할 때까지 계속 기록한다.
3.	10층 페이지는 내부 관리 단위이다.
4.	사용자에게 Stage 또는 Page를 표시하지 않는다.
5.	플레이어는 좌우로만 직접 이동한다.
6.	플레이어는 아이템 획득을 위해 같은 층을 여러 번 왕복할 수 있다.
7.	아이템은 통과 횟수를 기준으로 획득할 수 있다.
8.	아이템은 스코어형, 스킬형, 수집형으로 분류한다.
9.	수집형 아이템은 장기 저장 대상이다.
10.	뒤끝 서버는 추후 연결하지만, 서비스 인터페이스는 초기 구조부터 고려한다.
11.	한 번에 모든 기능을 만들지 않는다.
12.	각 단계마다 컴파일과 Inspector 연결 상태를 확인한다.
